Distance

Cost matrices between demand and supply feature vectors, and distances between curves or point sets. See Feature vectors and cost matrices.

AsymmEuclideanDistance

Generate a distance matrix of asymmetric Euclidean distances between two feature vector sets

Nickname: DMAsymm

Builds a cost matrix for Match that penalizes supply items that are too small. Demand and Supply are trees with one branch per object, each branch holding that object's feature vector (the layout of FeatureVector). For each pair the component computes the per-feature differences s - d (supply minus demand) and the Euclidean distance over all of them:

\[\mathrm{dist}_{ij} = \lVert s_j - d_i \rVert_2, \qquad \mathrm{cost}_{ij} = \begin{cases} \lceil \mathrm{dist}_{ij}^{\,p} \rceil & \text{if } s_{jk} \ge d_{ik} \text{ for every feature } k \\ \lceil \mathrm{dist}_{ij}^{\,q} \rceil & \text{otherwise} \end{cases}\]

with p = Power1 and q = Power2. A pair is "valid" when the supply item is at least as large as the demand in every feature, for example a reclaimed member that is at least as long as the required one and can be cut down. Valid pairs use Power1 (default 1); if the supply is smaller in even one feature, the whole distance, including the features where supply is larger, is raised to Power2 (default 2). The result is rounded up to an integer (Math.Ceiling). DistanceMatrix has one branch per demand item, paths {0}, {1}, ..., and item j of branch i is the cost of supply j for demand i.

Scaling. The penalty works only when distances are larger than 1: for a distance below 1, raising it to Power2 makes it smaller, and rounding up then gives a cost of 1 in both cases. Scale the features across demand and supply together, for example with PairNormalize (default Factor 100), so typical distances are well above 1. See EuclideanDistance for the effect of integer rounding.

Notes

  • Too-small supply is penalized, not forbidden: if it is cheaper overall, Match can still assign an invalid pair. Check the result.
  • The order matters: Demand is the "from" set and Supply the "to" set; swapping them changes which pairs are valid.
  • Error if the sets are empty or the vectors differ in length. Warning "Are you sure you want a power <= 0?" for Power1 ≤ 0, and a remark when Power2 ≤ Power1 (undersized supply is then not penalized more).
  • Costs saturate at 2147483647.

EuclideanDistance

Generate a distance matrix of Euclidean distances between two feature vector sets

Nickname: DMEuclidean

Builds the cost matrix for Match from two sets of feature vectors. Demand and Supply are trees with one branch per object, each branch holding that object's feature vector, which is the layout FeatureVector produces. For every demand vector d and supply vector s the cost is

\[\mathrm{cost}_{ij} = \left\lceil \lVert d_i - s_j \rVert_2^{\,p} \right\rceil\]

where p is Power: the Euclidean distance over all features is raised to Power and then rounded up to the next integer (Math.Ceiling). DistanceMatrix has one branch per demand item, with paths {0}, {1}, ..., and item j of branch i is the cost of assigning supply j to demand i. The metric is symmetric: swapping a demand and a supply vector gives the same cost. With Power 2 a large mismatch costs more relative to several small ones, so the assignment avoids single bad fits.

Scaling. Because costs are integers rounded up, the scale of the features decides the resolution. Any distance between 0 and 1 becomes a cost of 1, so features in the range 0 to 1 (scores, ratios) leave the solver almost nothing to distinguish. Features with very different magnitudes (a length in mm next to a score) let the large one dominate. Scale each feature across demand and supply together, for example with PairNormalize (or Normalize on a combined list), whose default Factor of 100 maps the largest value to 100.

Notes

  • Error if the sets are empty or any vector has a different number of values than the first demand vector.
  • Warning "Are you sure you want a power <= 0?" for Power ≤ 0.
  • Costs saturate at the largest 32-bit integer (2147483647); large raw features with Power 2 or 3 can reach it, which makes those pairs indistinguishable.
  • Lengths are in the Rhino document's units; DCT does not convert them.

FrechetDistance

Compute the Frechet distance between two curves

Nickname: Frechet

Measures how different two curves are as paths. Each curve is divided by arc length into Sample count equal segments (Rhino's divide-by-count with end points included, so an open curve gives Sample count + 1 points). The component then computes the discrete Fréchet distance between the two point sequences: the smallest possible "leash length" when one walker moves along each sequence from start to end, both moving forward only. It is computed with a dynamic programme over all point pairs, so time grows with the product of the two point counts.

Because the walk follows the point order, the result depends on curve direction: a curve and its reverse can have a large Fréchet distance even though they occupy the same place. Unlike HausdorffDistanceCurve, which only compares the point sets, it distinguishes curves that visit the same region in a different order. Use it to compare shapes of open curves that have been brought into a common position, for example with AlignToObject or AlignToPlane. The output is a single number per pair of curves; to use it as a matching cost, arrange the values yourself as a tree with one branch per demand curve and one item per supply curve, and feed it to Match.

Notes

  • The result is a length in the Rhino document's units. It is a discrete approximation; more samples give a value closer to the continuous Fréchet distance.
  • Remark "Frechet distances will work best for open curves; consider using the Hausdorff distance instead." when either curve is closed (the start point of a closed curve is arbitrary).
  • Errors: "Sample count must be at least 1"; "Could not divide the curves".

Second curveBCurveitemSecond curve
Sample countNIntegeritem50Number of segments each curve is divided into (closed curves give N points, open curves N + 1)

HausdorffDistanceCurve

Compute the Hausdorff distance between two curves

Nickname: HausdorffCurve

Measures how far apart two curves are as shapes. Each curve is divided by arc length into Sample count equal segments (Rhino's divide-by-count with end points included), and the Hausdorff distance between the two point sets is computed by brute force:

\[H(A,B) = \max\big(h(A,B),\, h(B,A)\big), \qquad h(X,Y) = \max_{x \in X} \min_{y \in Y} \lVert x - y \rVert\]

h(A,B) is the largest distance from a sample of A to the nearest sample of B. The result is the larger of the two directions, so it is symmetric: it is the farthest any part of one curve lies from the other curve. It does not depend on curve direction or start point, which makes it suitable for closed curves such as outlines and cross-sections.

Use it to compare outlines once they share a position and orientation, for example after AlignToObject, AlignToPlane or PlanarOutline. For open curves where the order along the curve matters, use FrechetDistance. For point sets, use HausdorffDistancePoints.

Notes

  • The result is a length in the Rhino document's units. It is measured between samples, so it is an approximation; more samples give a closer value. Time grows with the product of the two point counts.
  • Errors: "Sample count must be at least 1"; "Could not divide the curves".
  • Since v0.5 both directions are measured; earlier versions returned only h(A,B).

Inputs

First curveACurveitemFirst curve
Second curveBCurveitemSecond curve

HausdorffDistancePoints

Compute the Hausdorff distance between two sets of points

Nickname: HausdorffPoints

Computes the Hausdorff distance between two point sets by brute force:

\[H(A,B) = \max\big(h(A,B),\, h(B,A)\big), \qquad h(X,Y) = \max_{x \in X} \min_{y \in Y} \lVert x - y \rVert\]

For every point of one set the distance to its nearest point in the other set is found; h is the largest of these, and the result is the larger of the two directions. A small value means every point of each set has a close neighbor in the other. The point order and the point counts do not matter, and the two sets may have different sizes.

Use it to compare sampled geometry directly, for example the SampledPoints output of ObjectProperties for two objects after they have been brought into the same position with AlignToObject, or point clouds of scanned elements. For curves, HausdorffDistanceCurve samples the curves for you.

Notes

  • The result is a length in the Rhino document's units.
  • Time grows with the product of the two set sizes (every pair is compared), which is slow for large point clouds.
  • Error "Both point sets must contain at least one point" if either list is empty.
  • Since v0.5 both directions are measured; earlier versions returned only h(A,B).

ManhattanDistance

Generate a distance matrix of manhattan distances between two feature vector sets

Nickname: DMManhattan

Builds a cost matrix for Match from the Manhattan (L1) distance between feature vectors: the sum of the absolute differences of all features, rounded up to an integer.

\[\mathrm{cost}_{ij} = \left\lceil \textstyle\sum_k \lvert d_{ik} - s_{jk} \rvert \right\rceil\]

Demand and Supply are trees with one branch per object, each holding that object's feature vector, as produced by FeatureVector. DistanceMatrix has one branch per demand item, and item j of branch i is the cost of supply j for demand i. Unlike EuclideanDistance, each feature contributes in proportion to its difference, so one large mismatch is not weighted more than several small ones that add up to the same amount. There is no power input.

Use it where differences in separate features should simply add up, for example total offcut length over several dimensions. The same scaling advice applies as for the other distance matrices: costs are integers rounded up, so scale features across demand and supply together (for example with PairNormalize, default Factor 100) so that differences are well above 1 and no single feature dominates by its units.

Notes

  • The output branches are numbered {0}, {1}, ... like the Euclidean components. (Before v0.5.1 they reused the paths of the Demand tree; Match reads branches in order, so either works.)
  • Error if the sets are empty or the vectors differ in length.
  • Since v0.5 the sum is rounded up like the other metrics; earlier versions rounded down.
